# Image Studio 产品与实施方案

状态：方案草稿；产品定位、支付地区、收款主体和价格仍待确认。

当前阶段已完成 SvelteKit 首页原型、基础健康检查、SQLite schema 和数据库约束测试；账号、图片生成和支付仍未接入。页面上的生成按钮保持禁用，避免把尚未配置的服务误认为可用。

## 1. 目标

Image Studio 是一个只做一件事的网站：用户输入图片要求，选择画幅，生成图片并下载。API 密钥只保存在服务端，用户不需要接触模型配置。

首个目标不是做通用的模型平台，而是验证三件事：

- 用户能否在不配置 API 的情况下完成一次生成；
- 每张图的实际成本、耗时和失败率是否可控；
- 用户是否愿意购买生成点数。

建议首版面向邀请制内测，默认中文界面，采用点数包付费；自动订阅在付费流程验证后接入。这些是本方案建议，并非已经确定的商业配置。

## 2. 产品范围

### 首版包含

- 输入提示词、选择画幅和生成质量；
- GitHub 横幅、头像、项目封面等快捷模板；
- 任务状态：排队、生成中、成功、失败、结果待确认；
- 图片预览、下载、最近作品；
- 用户账号、点数余额和消费记录；
- 点数包订单、支付回调和订单查询；
- 管理端查看订单、任务、成本和异常任务。

### 首版明确不包含

- 多模型自由切换；
- 用户上传参考图和图像编辑；
- 团队空间、API 对外转售；
- 自动月度订阅；
- 无限生成或不设上限的免费额度。

## 3. 推荐架构

先使用一个 SvelteKit 单体应用，前后端同仓库：

```text
浏览器
  │
  ▼
SvelteKit 页面与 API
  ├── 账号与会话
  ├── 点数账本与订单
  ├── 生成任务队列
  └── OpenAI-compatible 图片 API
          │
          └── 对象存储（生产环境）
```

- 首版用 SQLite，限定单台服务器、持久化磁盘和短事务，开启外键与 WAL，并完成备份恢复验证。需要多实例写入时再直接迁移 PostgreSQL，不提前维护两套数据库路径。
- 图片先放服务器持久化目录，通过检查作品归属的下载接口读取；数据库只保存元数据。扩大规模后迁移 S3 兼容对象存储。
- API 地址、API Key、模型 ID 只从部署环境变量读取；不会读取 `~/.codex/auth.json`，也不会把个人 Codex 凭据带进网站。
- 首版用数据库持久化任务，由单个后台 worker 取任务；不引入 Redis。认领任务须为原子操作。进程重启后，未调用上游的排队任务可以继续，已经发送的任务先核查结果，不能直接重新提交。

## 4. 计费设计

首版建议采用点数包：例如 10 点、30 点、100 点，仅为展示结构，尚未定价。服务端根据已验证的模型、尺寸、质量计算点数消耗；提交时冻结这次任务的价格和模型，避免调价影响既有任务。币种根据收款地区确定。

一次生成的结算流程：

```text
提交任务 → 原子预占点数 → 调用图片 API
                       ├─ 成功：结算预占
                       ├─ 明确失败：释放点数
                       └─ 超时/断线：标记“结果待确认”，禁止盲目重试
```

账本必须追加写入；余额快照、账本记录和任务状态必须在同一事务内更新，禁止脱离账本直接修改余额。回调先验证签名，再核对平台商户、订单、支付状态、金额和币种，以平台交易标识做幂等约束；重复通知不能重复加点。金额使用对应币种最小单位的整数，点数使用整数，避免浮点误差。

支付回调验证和入账由服务端完成，浏览器的“支付成功”跳转不能作为到账依据。退款也要有独立记录：确认支付平台退款状态，并记录对应点数调整；退款范围和已消耗点数的处理规则在收费前公开。首版可人工审核退款，不能直接删订单或改账本。

真实单图成本应包含失败请求消耗。先按模型、尺寸、质量实测，再结合存储、支付手续费和退款损耗定价，不直接按剩余免费额度决定售价。新任务须原子预留用户点数与全站预算；不确定消耗继续占用预算，明确结算后再调整。应用侧预算限制配合上游限额使用，估算值不能承诺绝对支出上限。

订阅放到第二阶段：在点数账本稳定之后，再增加周期订单、续费、取消、到期和未用点数规则。这样点数包和订阅共用同一套账本，不需要重做计费核心。

## 5. 主要数据

- `users`：账号和状态；
- `sessions`：服务端会话；
- `credit_accounts`：当前可用与预占点数；
- `credit_entries`：充值、预占、结算、释放的不可变账本；
- `orders`：支付订单、金额、币种、点数和支付状态；
- `generation_jobs`：提示词、画幅、模型、点数成本、状态和错误信息；
- `assets`：生成图片的对象存储地址、尺寸、保留时间；
- `provider_attempts`：上游请求的安全摘要、状态和可核查信息，不保存密钥。

生成任务和点数账本通过用户 ID 关联；任何读取作品、订单或任务的 API 都必须检查所属用户。

## 6. API 边界

- `POST /api/generations`：校验输入、预占点数、创建任务；
- `GET /api/generations/:id`：查询本人任务状态和结果；
- `GET /api/assets`：查询本人历史作品；
- `GET /api/billing/packages`：读取当前点数包；
- `POST /api/orders`：创建待支付订单；
- `POST /api/payments/webhook`：验证支付回调并幂等入账；
- `GET /api/me`：读取会话、余额和权限；
- `GET /api/health`：部署健康检查。

每个生成请求接受幂等键；重复提交同一幂等键只能得到原任务，不能重复扣点或重复调用上游。

## 7. 实施阶段

### 阶段 0：确认商业边界

- 确定收款地区、主体和支付渠道；
- 实测可用图片模型、画幅、质量、耗时和单次成本；
- 确认免费额度、点数包价格、图片保留时间和每日预算。

验收：有一张模型与成本表，并选定一个支付渠道；没有确认前不接真实支付。

### 阶段 1：生成工作台

- 完成首页、提示词输入、模板、画幅选择和结果状态；
- 接入一个明确配置的图片 API；
- 完成成功、失败、超时待确认和下载流程。

验收：测试账号能完成一次真实生成；刷新页面后仍能找回任务；API Key 不出现在浏览器或日志。

### 阶段 2：账号与点数账本

- 增加登录、会话、余额和历史记录；
- 完成预占、结算、释放和幂等键；
- 增加每日次数、并发数和全站预算限制。

验收：并发提交不会负余额；同一任务不会重复扣点；上游明确失败会退回点数；不确定结果不会自动重试。

### 阶段 3：点数包支付

- 创建订单和待支付页面；
- 接入一个支付渠道的签名校验和回调；
- 增加订单查询、支付失败、重复回调和人工补单记录。

验收：沙盒支付只入账一次；用户只能看到自己的订单；支付密钥和回调原文不进入前端。

### 阶段 4：上线保障

- 单服务器部署、HTTPS、SQLite 与图片的持久化目录、备份；
- 结构化日志、错误告警、成本统计和管理员入口；
- 速率限制、提示词长度限制、内容安全策略和图片自动清理。

验收：重启后任务和订单状态可恢复；超过预算会停止新任务；数据库和图片有恢复方案。

### 阶段 5：订阅与扩展

- 月度订阅和周期扣款；
- 订阅点数规则、取消、退款和到期处理；
- 参考图、图像编辑、多模型路由和团队功能。

进入条件：点数包已有持续付费用户，且成本、失败率和退款原因有真实数据支持。

## 8. 关键质量指标

- 生成成功率；
- P50/P95 生成耗时；
- 每张成功图片的真实成本；
- 预占点数与最终结算的差异；
- 支付成功率和重复回调拦截数；
- 任务重复提交率、待确认任务数量；
- 用户复用率和点数包购买转化率。

## 9. 风险与边界

- 上游超时可能已经产生费用：结果待确认状态必须优先于重试；
- 几个用户并发生成即可迅速消耗额度：必须有账户、全站并发和预算闸门；
- 公开开放会带来滥用和内容审核压力：先邀请制，再逐步开放；
- 支付渠道取决于收款主体与地区：没有明确渠道前，不把支付 SDK 写死；
- 生成图片和提示词可能包含个人信息：默认短期保留，提供删除入口，并限制管理员访问。

## 11. 工程约定与验证

建议目录：`src/routes` 放页面与接口，`src/lib/server` 放只在服务端执行的账号、生成和计费代码，`db` 放顺序迁移，`tests` 放数据库与业务测试，`e2e` 放浏览器流程，`docs` 放产品规格。

已声明的命令如下；当前代码尚未齐全，不代表这些命令都已通过：

```bash
pnpm install
pnpm dev
pnpm check
pnpm test
pnpm test:e2e
pnpm lint
pnpm build
```

使用 TypeScript 严格模式、单引号和 Prettier；例如服务端先用参数绑定检查本人任务，再返回必要字段：

```ts
const job = db
  .prepare('SELECT id, status FROM generation_jobs WHERE id = ? AND user_id = ?')
  .get(jobId, userId);
```

关键测试优先覆盖实际账目结果：并发预占不超额、重复回调只入账一次、重复生成请求只创建一个任务、明确失败只释放一次、超时不自动重发、跨用户访问被拒绝。浏览器检查包含移动端输入、刷新找回任务、预览下载和支付结果查询；真实 API 与支付沙盒验证属于单独的联调步骤，不放入默认测试。

本次只补充方案。后续本地开发可在既定范围内继续；真实扣款、正式发布、退款及生产数据操作须按届时明确授权执行。禁止提交密钥、从客户端决定点数或价格、删除账本记录、将开发模拟结果显示为真实生成或支付成功。

当前是单个本地项目，没有远程仓库或 issue 跟踪要求；阶段任务先由本规格管理，后续建立远程仓库时再按可独立验收的功能划分 issue。
